# ЛР4: горизонтальное масштабирование

Папка содержит отдельную копию приложения из ЛР3 в namespace `vp-lr4`, сценарий k6 с постоянной интенсивностью, экспорт dashboard Grafana, исходные результаты и отчёт. Снимки терминала и Grafana получены из работающих программ. Пароль администратора в проекте не хранится.

## Воспроизведение

Запустить прежний K3s командой `sudo k3s server` в отдельном терминале. Затем из этой папки:

```bash
export KUBECONFIG="$HOME/.kube/config"
helm upgrade --install vp-lr4 ./target-chart -n vp-lr4 --create-namespace -f target-chart/values-lab4.yaml
k3s kubectl apply -f service-monitor.yaml
k3s kubectl rollout status deployment/auth-service -n vp-lr4
k3s kubectl -n monitoring port-forward svc/prometheus-kube-prometheus-prometheus 9090:9090
```

Последняя команда остаётся работать в отдельном терминале. Для dashboard в другом терминале:

```bash
k3s kubectl -n monitoring port-forward svc/prometheus-grafana 3000:80
python3 grafana_api.py source
python3 grafana_api.py install
```

Адрес Prometheus внутри кластера при сетевых настройках этого компьютера пришлось указать как IP пода в `prometheus-values.yaml`. После пересоздания пода найдите актуальный адрес командой `k3s kubectl -n monitoring get pod prometheus-prometheus-kube-prometheus-prometheus-0 -o wide` и обновите Helm release мониторинга. В values также выключено автообновление встроенных плагинов Grafana: при перезапуске оно удаляло работающий плагин Prometheus и не могло записать новую версию в доступную только для чтения папку образа.

Для нового опыта используйте адрес NodePort текущего узла. На этой машине `localhost:30083` не отвечает, поэтому использован адрес узла `10.186.226.238:30083`; при смене сети он может измениться.

```bash
TARGET_URL='http://АДРЕС_УЗЛА:30083/work?iterations=20000' python3 run_scaling.py
```

Скрипт последовательно масштабирует `auth-service` до 1, 2 и 3 реплик, ждёт готовности и запускает один сценарий k6 на уровнях 10, 25, 50 и 100 запросов/с по 60 секунд. Между прогонами выдерживается пауза. Каждая пара конфигурации и интенсивности сохраняется в `results/` как исходный вывод k6, JSON k6, ответы Prometheus и строка `summary.json`. Успешно завершённые пары при повторном запуске пропускаются. Порог k6 может сделать exit code ненулевым; результат всё равно сохраняется для анализа, если JSON был создан.

`/work?iterations=20000` вычисляет SHA-256 в цикле и возвращает имя обслужившего Pod. Число итераций во всех тестах одинаковое. Мониторинг приложения через `/metrics` сохранён.

После эксперимента:

```bash
python3 capture_terminal.py
python3 build_report.py
```

Снимки Ptyxis показывают именно команды просмотра сохранённого вывода, а не изображают новый запуск теста.

## Что получилось

Проведены все 12 прогонов: 1, 2 и 3 реплики при цели 10, 25, 50 и 100 запросов/с. При одинаковых критериях p95 < 500 мс, ошибок < 1% и без пропущенных итераций максимальные **измеренные** устойчивые уровни составили примерно 25, 50 и 50 RPS. Для трёх реплик при цели 100 RPS получено 98,04 RPS, но p95 вырос до 1200 мс и k6 пропустил 94 итерации. Между 50 и 100 RPS дополнительные уровни не измерялись, поэтому точный предел трёх реплик по этим данным определить нельзя.

В таблицах отчёта клиентские RPS, p95 и ошибки взяты из JSON k6. CPU и память рассчитаны из сохранённых ответов Prometheus за последние 30 секунд каждого прогона. Графики Grafana показывают те же сохранённые временные интервалы. Исходные файлы эксперимента лежат в `results/`, а не получены из изображений отчёта.
